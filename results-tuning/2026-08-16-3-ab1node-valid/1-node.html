What this makes visible: the default really does run 1–16 channels below 512 KB, which is the whole headroom the config exploits. From 2 MB up, config and default converge on the same selection — which is why the curves coincide there.

This table is also how the ≥64 MB bug was caught. In the first run the config selected RING*/SIMPLE/14 against the default's 56: the ÷4, visible in the selection columns rather than guessed at from the bandwidth drop. After the fix both arms read RING*/SIMPLE/56, as shown above.

Caveat: -A 1 is trustworthy for algorithm and protocol, but its channel column reports a planned ceiling. Real per-channel spans come from NCCL_DEBUG=INFO channel{Lo..Hi}. Under WarpSpeed the figure shown is the base count, which is why 56 appears where 224 channels actually run.

Why the config wins at small sizes

RCCL's 1-node default uses very few channels below 256 KB — 1, 1, 1, 2, 4, 8, 16 for 4 KB through 256 KB. The tuned config raises those to 24–48 and switches protocol where measured to help. Pushing channel count up was the untested direction; every earlier experiment in this project forced it down, which always hurt.

The ≥64 MB channel-unit bug — found, fixed, re-measured

At ≥64 MB RCCL enables WarpSpeed by itself (RING* in the logs), which multiplies the channel count by 4. Nobody asks for it — both arms get it.

It changes what a channel number means. The sweep set channels through an environment variable, which sets the base count. The plugin's channels field is the post-multiplier total. Same integer, four times the meaning — so a config that copies the swept number straight into a plugin rule under-provisions by 4×.

The plugin log confirms the mechanism directly: WarpSpeed enabled: warpSpeedChannelMultiplier 4, maxNchannels 448, nc 224, and both arms then report RING* SIMPLE 56.

The rule: multiply the swept channel count by 4 before writing it into a plugin rule wherever WarpSpeed applies. The charts above are the corrected run — the −60% hole is gone.

The fix buys safety, not speed. With the right channel count the config matches the default at ≥64 MB (−0.0%), so the rule is correctly dropped and those sizes fall through to RCCL. Nothing beats the default there. What the fix removes is a rule that would have cost 60% in production.

What made this run trustworthy

An earlier attempt the same day, with the identical config on the identical node, kept 0 of 11 rules. The difference was GPU clocks.

The GPUs idle at ~195 MHz against a ~2400 MHz peak, and each repeat is a separate srun. The first four repeats measured a GPU still ramping:

4 MB, default armr1r2r3r4r5r6r7
cold (first attempt)92.891.188.490.1128.1128.1127.8
with warm-up127.5128.3128.3128.3127.9127.5128.0

The step appears in both arms at every size, so it never biased which arm won — but it inflated each arm's own spread to ~40%. P(sup) is a rank statistic, so overlapping arms collapse it below the 0.95 gate and every rule was rejected despite gains up to +47.9%.

-w/--warmup does not cover this: those are iterations inside one launch, microseconds at small sizes, warming caches rather than clocks. The fix is --warmup-runs 4, discarded runs before the measured repeats.

Two guards were added as a result. The harness now refuses to issue verdicts when within-arm spread exceeds a threshold — a run that cannot decide is reported as NOT VALID rather than as evidence that RCCL's defaults are optimal. And a mixed rule range is now split into its passing sub-ranges instead of being discarded whole.

How this compares to the 2026-08-04 run

The tolerance change was expected to matter more than it did here: at 1 node the sweep was only giving away ~2.5% by picking fewest-channels within a 5% window. At 2 and 3 nodes the give-away was 2.9% and 3.5%, and the resulting configs differed at 10 and 8 sizes respectively — but those A/Bs could not be measured (see limits below). So 1% remains unproven as an improvement; its case rests entirely on multi-node.

What this run does establish: the 1-node result reproduces independently 12 days later, on a fresh allocation, with a materially changed harness. Two agreeing runs is a stronger claim than one.

Scope and limits

  • 1 node only. The 2-node and 3-node A/Bs on the same day were void — a co-tenant job was saturating the shared fabric, and repeats of the same configuration ranged 1.5–25 GB/s. Multi-node needs a quiet cluster; single-node never touches the fabric, so this result is unaffected.
  • all_reduce only. No other collective was swept.
  • RCCL 2.28.3-develop:2e42aa8. The acceptance map is version-specific.
  • Sweep and A/B bandwidth are not comparable — the sweep runs under mpirun outside Slurm. Each A/B is self-contained: both arms under srun, interleaved, identical logging.
  • Plugin firing verified in every per-rank INFO log via TUNER/Plugin: Applied config.
