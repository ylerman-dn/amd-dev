Does RCCL's default leave anything on the table?

Two weeks: getting the tuning harness honest enough to believe, then A/B-ing a generated config against RCCL's own default at 1, 2 and 3 nodes — to get a feel for whether there is real value here.

ylerman
all_reduce · 4K–512M · RCCL 2.28.3-develop
nodes amd-mi355x-5,6,7 · 8 GPUs each

Background

RCCL makes three choices on every collective call

What I did first

The sweep tool needed work before its output meant anything

There was already a sweep tool in the repo. I went through it and refreshed it — three things were quietly wrong, and any one of them was enough to make every number downstream meaningless:

  • It asked the benchmark for the wrong report, so it never saw what actually ran.
  • It recorded what it requested, not what RCCL selected — and RCCL substitutes silently. About a third of the previous config named combinations the library cannot deliver.
  • It ranked candidates on a column that was not bandwidth. At one point that made it prefer configs 99% slower than the default.

Every row now carries requested and measured algorithm, protocol and channel count, and flags the row when the two disagree. That is what made the rest of this worth running at all.

Also looked at Optuna for the search itself. Today it is a plain grid sweep — a few hundred runs. Bayesian search is the obvious upgrade, but there is no point pointing a smart optimiser at an objective you do not yet believe.

Result · 1 node

Small and mid message sizes are wide open

RCCL default generated config log scale · 7 repeats per arm, interleaved

RCCL uses 1–16 channels below 256K. Pushing that count up is worth +12% to +63% — and every rule we kept won all 49 head-to-head pairs against the default.

The collapse from 64M is our own bug, not the hardware: the plugin's channel field means something different from the environment variable we swept with, so we deployed 4× fewer channels than intended. The validator caught it and refused to ship it.

Result · 2 and 3 nodes

Multi-node defaults are already tight

shipped win verified win, not shipped faster, not significant slower

Above 128K the default already sits at the 48-channel cap, so there is no channel headroom left. The wins that do exist come from algorithm choice — TREE→RING at 32M — not from retuning channels.

The two outlined bars are the interesting failure: verified wins of +8.9% and +12.1% that never shipped, because the generator merged them into a size range that also contained a regression.

What I don't trust yet

The numbers are real. The pipeline isn't finished.

  • The selection step gives away ~3.5% at 9–11 message sizes per multi-node scale. It keeps every candidate within 5% of the best and then prefers the fewest channels — but real run-to-run spread is ~0.7%, so that window swallows almost everything and channel count decides instead of bandwidth. We measured faster configs and shipped slower ones.
  • Rule ranges bury wins. Merging adjacent sizes keeps the config compact, but a range holding one win and one regression is correctly rejected whole — losing both.
  • Narrow scope. all_reduce only, one RCCL version, and co-tenants shared the fabric during the multi-node runs — which moves absolute bandwidth, not the A/B contrast.

None of this invalidates the measured gains — each was A/B'd against the default under identical conditions, interleaved. It means the tool is currently under-delivering, which is a good problem to have.

Where I'd take it

First make the tool deliver good value — then widen it

  • Finish the tuning loop. Fix the selection tolerance and the rule granularity, regenerate from the sweep data we already have, re-run the A/B. No new sweep needed — the cheapest value on this list.
  • Extend rccl-tests. Past all_reduce, and toward a harness we can point at any collective without hand-driving it.
  • Smarter search. Optuna over the grid, once the objective is worth optimising against.
  • Understand the plugin properly. The channel-unit surprise cost 65% and we found it by accident. Worth knowing what else it reinterprets before trusting it anywhere real.
