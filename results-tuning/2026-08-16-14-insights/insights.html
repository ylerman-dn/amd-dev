What we learned tuning RCCL on MI355X

Everything below is measured, not inferred. Plain language, one idea per section.

2026-08-16 · all_reduce · gfx950 · RCCL 2.28.3-develop:2e42aa8 · 8 ranks × 1 GPU per node

The single most useful thing we found: RCCL switches algorithm and protocol too late at multi-node — five times out of six, and never too early. Every multi-node win we verified is one of those late switches. We have been fixing them one message size at a time.

1Two completely different problems

One node: RCCL uses too few channels. That is the whole story.
Two or three nodes: channels are already right. The switch points are wrong.

At 1 node the default runs 1, 1, 1, 2, 4, 8, 16 channels for small messages where 24–56 is best. Turn the number up, gain 19–67%. At multi-node it already sits at 48 (the cap) nearly everywhere and there is almost nothing to gain by changing it.

So "tune RCCL" means two different jobs depending on scale. A method that works at one scale may find nothing at the other.

Five of six late. None early. That is a systematic bias, not random error — and it means the cause is upstream, in the constants RCCL computes those switch points from.

At 1 node there is a different error: RCCL goes straight from TREE/LL to RING/SIMPLE and never uses RING/LL at all — yet RING/LL is the best choice from 256K to 1M. It skips a whole regime.

4More channels is not always better

Everyone assumes bandwidth rises with channel count. True for TREE. For RING at multi-node small and mid sizes it collapses:

2 nodes, 256K, RING/LL      8 channels -> 5.96 GB/s
                           48 channels -> 2.13 GB/s     -64%

38 curves at 2 nodes and 35 at 3 nodes lose more than 3% by going to maximum channels. Several lose more than half.

This is also the whole explanation for the famous 3-node 128M dip:

3 nodes, 128M, RING/LL128   32ch -> 256.4    40ch -> 271.4 (peak)    48ch -> 243.9

The default uses 48 because that is the cap. The peak is at 40. Not a fabric problem, not a bug — over-provisioning past the optimum.

Consequence for any search method: you cannot assume the channel curve is monotonic and stop climbing early. It has a peak, and the peak moves with size and algorithm.

The lesson is not the individual bugs. It is that the tool reported success throughout. Every gate added afterwards exists because something passed silently.

7Three environmental traps

GPUs start cold. They idle at 195 MHz against a 2400 MHz peak. The first runs after an allocation measure the ramp, not the hardware. One run kept 0 of 11 rules; the identical config kept 7 of 11 once warm. 2 nodes need ~4 warm-up runs, 3 nodes need ~8.

A monitoring daemon disturbs multi-node runs. amd-nic-metrics spawns 9 nicctl processes polling RDMA queue-pair stats every ~30 s for ~9 s. Runs take 11–15 s, so about a third land in a poll and come back 10× slow.

Co-tenants matter less than expected. Nodes 5 and 7 share a leaf switch, so traffic between them never reaches the spine another job is using. We wrongly blamed a neighbour job for hours before measuring it properly.

The median is tiny; the tail is huge. Most points repeat within 1%; a few stall completely. Two consequences: the old 5% equivalence tolerance was ~7× the real noise and declared genuinely different configs tied (now 0.5%), and a single stalled run can sink a good rule — one did, scoring a real +7.6% gain at P(sup) 0.86 because one repeat came back 16× slow.

One repeat is usually fine and occasionally costs a win. The configs that swap places are genuinely close, so it rarely matters — but sometimes it does. The A/B protects you either way: a weak candidate still has to beat the default over 7 repeats, so a 1-repeat sweep risks missing a win rather than shipping a bad rule.

Rule of thumb: 1 repeat to find where the wins are, 3 repeats to measure them properly.

10The "smart search" in the tool does nothing here

Hotspots detected: 0      Iterations: 1      (1, 2 and 3 nodes alike)

The hotspot loop looks for bandwidth dropping as size grows. Bandwidth rises monotonically, so on a healthy curve there is nothing to find. And the one real dip — 3 nodes at 128M — is 8.4%, below its own 10% trigger.

Its apparent 3× speed advantage came entirely from doing 1 repeat instead of 3. The orchestration part of that script is genuinely useful; the hotspot part is not, as configured.

11The trap that cost 65%

Where WarpSpeed is active (≥64 MB, 1 node), RCCL multiplies the channel count by 4.

channels set by environment variable  ->  that is the BASE count
channels set in a plugin rule         ->  that is the POST-MULTIPLIER TOTAL

Same integer, four times the meaning. We swept 48 via env var, wrote 48 into the config, and deployed 12 base / 48 actual against the default's 56 base / 224 actual. Measured −60.3%. Writing 224 restores parity exactly.

The general rule this illustrates: the path you measure on must be the path you deploy on, or you are not measuring what you ship.

12What to do next, in order of value

1. Fix the cause, not the symptoms. RCCL supports a v5 tuner plugin that lets a plugin rewrite its internal cost-model constants — latencies and per-channel bandwidths per algorithm and protocol. Those constants produce the switch points in section 3. We are on v4, which only overrides outcomes size by size. Correcting the constants could fix all six late transitions at once, and would apply to collectives we never swept.

2. Sweep the other five collectives. Everything we know is all_reduce. The split in section 1 is a prediction for the others, not a fact.

3. Find out which message sizes your workload uses. We can prove each rule helps. We cannot say what the config is worth to you, because that depends entirely on your size distribution — a model doing mostly 4 MB all_reduces gains nothing from our 1-node config; one doing 512 KB gains 65%. This is the missing denominator under every number here.

4. Reduce runs only if the space grows. 54 configs per collective-scale takes ~35 minutes exhaustively. Smarter search pays once the space is much bigger. Expect roughly half the runs from pruning, not a tenth.
