How RCCL's DDA all-reduce works: one-shot, two-shot, the GPU barrier, IPC and XGMI

Read from source, not from docs. Tree: github.com/ROCm/rocm-systems, clone /home/dn/ylerman/wg/rocm-systems, projects/rccl/. Files quoted at the 2026-06-29 state (local HEAD a98014c18b), which is the code our image runs: RCCL 2.30.4-HEAD:6b0e43f logs ncclDdaIpcCommInit: scratch 67108864 bytes, IpcGpuBarrier nBlocks=24 (rank logs of the 2026-09-14 D run on node 2, /data/ylerman/csvtuner-2026-09-14/qwen/csv_tun/logs/rccl.amd-mi355x-2.*.log.gz), the constants of that tree. The September origin/develop (b70c089619, 2026-09-14) has the same two kernels line for line after a rename (meta::comms → dda::common, files moved to src/algorithms/dda/); the differences that matter are listed at the end.

In one paragraph. At communicator creation every one of the 8 GPUs allocates a 64 MiB "scratch" buffer and a small "mailbox" of flags in uncached VRAM, exports them with HIP IPC, and opens the other seven so that each GPU holds device pointers into its peers' memory. An all-reduce is then one kernel launch on each GPU, no channels, no protocol, no proxy thread: every GPU copies its input into its own scratch, all eight meet at a GPU-side barrier (flags in the mailboxes), then each GPU reads its peers' scratch directly over XGMI and adds. Up to 256 KB every GPU reads everything and reduces the whole vector itself (one-shot, 2 barriers). Above 256 KB each GPU reduces only its 1/8 slice, writes the result back into its own scratch, another barrier, and everybody gathers the eight reduced slices (two-shot, 3 barriers, four times less traffic). The whole thing happens before RCCL's algorithm/protocol/channel selection, so a tuner never sees it.

2. One-time setup at communicator creation

ncclDdaIpcCommInit (src/ipc_init.cu:33-167) runs once per communicator, from ncclCommInitRank (src/init.cc:2571). It builds three things on every GPU:

Fig. 2. Setup. Handles travel once over the host bootstrap sockets; data never touches the host afterwards.

2.1 What "IPC" means here

  1. Export. hipIpcGetMemHandle turns a device allocation into a 64-byte opaque handle that another process on the same machine can use (ipc_mem_handler.cc:52). RCCL runs one process per GPU (SGLang TP-8 too), so the eight ranks are eight processes: ordinary pointers are meaningless across them, handles are not.
  2. Exchange. The handles are all-gathered with the NCCL bootstrap network (bootstrapAllGather, ipc_mem_handler.cc:53), the same host TCP ring RCCL used to set up the communicator. 8 × 64 bytes, once.
  3. Import. hipIpcOpenMemHandle(…, hipIpcMemLazyEnablePeerAccess) (ipc_mem_handler.cc:59-62) maps the peer's allocation into the local process's GPU address space and enables peer access on the way. From now on ipcbuffs[p] is a normal device pointer; a kernel dereferences it like local memory.
  4. Peer table. The eight resulting pointers (index = rank, own rank included) are copied into a tiny device array (ipc_init.cu:104-122) and passed to every DDA kernel as ipcbuffs.
  5. The barrier owns a second ncclIpcMemHandler and does the same three steps for its mailbox (ipc_gpu_barrier.cu:71-105).

Contrast with the classic RCCL path: there, data moves through RCCL's own per-channel FIFO buffers with a protocol (Simple/LL/LL128) that interleaves flags with data, driven by ring or tree steps. DDA has none of that machinery: two buffers per GPU, one kernel, the user's data is reduced straight out of the peers' scratch.

2.2 Why uncached memory

Both scratch and mailbox are allocated with hipDeviceMallocUncached (fine-grained fallback on old HIP; ipc_init.cu:64-68, device_buffer.cc:33-37). A peer GPU reads this memory over XGMI; if the owner's L2 held a newer copy of a line, the peer would read stale HBM. Uncached (fine-grained) memory makes every write visible at the memory side without a cache flush, and it is the memory kind on which cross-GPU atomics (the barrier's compare-and-swap) are coherent. The price is that the owner's own accesses to its scratch are also uncached, which is one reason the kernels touch scratch exactly once per element.

2.3 What XGMI contributes

XGMI is the GPU-to-GPU Infinity Fabric on the MI355X board; all 8 GPUs are directly connected. Once a peer allocation is mapped, a kernel's ordinary 16-byte load from ipcbuffs[p][i] becomes a read transaction across the XGMI link to GPU p's HBM, with no copy engine, no host, no intermediate buffer. This is the "direct" in Direct Data Access. In the classic path a rank never reads a peer's memory; it writes into the peer's FIFO and the peer reads locally. DDA turns the dataflow around: the consumer pulls what it needs, and pulls from all seven peers in parallel (the reduce loop issues the eight loads back to back, CollCommon.h:129-139). The gfx1250 "fabric" variants added later (MNNVL-style) are a different transport and are not compiled in for gfx950 (ipc_init.cu:48-56 gates to gfx942/gfx950).

3. One-shot ("flat") kernel: messages up to 256 KB

ddaAllReduceFlatIpc, src/include/algorithms/all_reduce/all_reduce_dda.h:17-50. Chosen when sizeBytes <= kDdaFlatTreeThresholdBytes = 1 << 18 (256 KB, dda_all_reduce_ipc.cu:31, 55), or when the count is not divisible by 8.

Fig. 3. One-shot. Each GPU ends with the full result after reading the full input of all peers.

// all_reduce_dda.h:36-49, condensed
copyFromSrcToDest(sendbuff, ipcbuffs[selfRank], idxStart, count, idxStride);   // A: stage my input in MY scratch
barrier.syncOnSameBlockIdx<true, true>();                                       // B: all 8 staged, visible
reduceScatter<T, 8, hasAcc>(ipcbuffs, recvbuff, acc, selfRank, idxStart, count, idxStride, /*pattern=*/2); // C: recv[i] = sum_r ipcbuffs[r][i]
barrier.syncOnSameBlockIdx<true, false>();                                      // D: all 8 finished reading

Traffic per GPU: N bytes written locally, 7N bytes read over XGMI (N = message size). Latency: two barriers. For a 128 KB decode all-reduce that is 896 KB of XGMI reads per GPU, roughly a microsecond of wire time, so the barriers and launch dominate, and doing the reduction eight times redundantly is cheaper than adding a third barrier.

4. Two-shot ("tree") kernel: messages above 256 KB

ddaAllReduceTreeIpc, all_reduce_dda.h:52-96. The name "tree" is historical; it is reduce-scatter followed by all-gather, the same skeleton as every bandwidth-optimal all-reduce. Rank r "owns" slice r (elements [r·N/8, (r+1)·N/8)).

Fig. 4. Two-shot. Each GPU reduces one eighth and gathers seven eighths.

// all_reduce_dda.h:64-95, condensed (memcpyAsync sendbuff -> scratch happened in the stream just before)
barrier.syncOnSameBlockIdx<false, true>();                                        // 1: all 8 staged
reduceScatter<T, 8, hasAcc>(ipcbuffs, ipcbuffs[selfRank], acc, selfRank, idxStart, count/8, idxStride, /*pattern=*/1); // 2: my slice, in place
barrier.syncOnSameBlockIdx<true, true>();                                         // 3: all 8 slices reduced
allGather<T, 8>(ipcbuffs, recvbuff, selfRank, idxStart, count/8, idxStride, /*enable_offset=*/true); // 4: collect 8 slices
barrier.syncOnSameBlockIdx<true, false>();                                        // 5: all 8 done reading

Traffic per GPU: N bytes memcpy locally, 7N/8 XGMI reads in the reduce-scatter, 7N/8 in the all-gather: 1.75N over the wire against 7N for one-shot, four times less. Latency: three barriers plus a separate memcpy launch. The in-place trick (write the reduced slice back into the same scratch it was read from) is safe because slice r is read by rank r only, and each thread writes exactly the 16 bytes it just read.

Why the split is at 256 KB. The two kernels move 7N and 1.75N bytes over XGMI and pay 2 and 3 barriers respectively. A barrier round is a few microseconds of flag ping-pong across the fabric, independent of N; the wire time grows with N. Below a few hundred KB the barrier saved by one-shot outweighs the 5.25N of extra reads; above it the reads win. kDdaFlatTreeThresholdBytes = 1 << 18 is a hard-coded constant, not an env var (dda_all_reduce_ipc.cu:31). For our models this puts Qwen d32 (128 KB), gpt-oss d32 (180 KB) on one-shot and every larger decode/prefill size on two-shot.

5. The GPU barrier, in detail

IpcGpuBarrier::syncOnSameBlockIdx, src/include/ipc_gpu_barrier.h:112-148. Nothing runs on the host during an all-reduce; the eight kernels synchronise among themselves through flags in the mailboxes.

5.1 Layout

Each GPU owns one mailbox: nRanks × nBlocks = 8 × 24 32-bit flags, index block·8 + rank (ipc_gpu_barrier.h:87-89). Flag [b][s] in GPU d's mailbox means "block b of GPU s has arrived at the barrier, for GPU d". Every GPU holds pointers to all eight mailboxes (its own plus seven IPC-mapped), so a GPU can write into any peer's mailbox and only ever waits on its own.

blocks, columns are sender ranks. Block b of GPU 3 waits only on row b of its own mailbox: eight flags, one per sender (its own included). Only eight threads of each block take part (threadIdx.x < 8, ipc_gpu_barrier.h:131): thread p talks to GPU p. 24 blocks × 8 ranks × 4 B = 768 B per mailbox. Tiny, but it is the hottest memory in the whole algorithm.

Fig. 5. One mailbox. Every barrier is a row-wise all-to-all of single 32-bit flags.

5.2 The algorithm of one barrier

// ipc_gpu_barrier.h:112-148, annotated
template <bool hasPreviousMemAccess, bool hasSubsequentMemAccess>
void syncOnSameBlockIdx() {
  if (hasPreviousMemAccess) __syncthreads();          // (1) all 512 threads of MY block finished their loads/stores
  if (threadIdx.x < 8) {                                // (2) eight threads, one per peer
    peer = threadIdx.x;
    allMailboxes_[peer].setFlag…(selfRank_, blockIdx.x);   //   put 1 into PEER's mailbox at [my block][my rank]
    allMailboxes_[selfRank_].waitFlag…(peer, blockIdx.x);  //   wait until MY mailbox [my block][peer] holds 1, then reset it to 0
  }
  if (hasSubsequentMemAccess) __syncthreads();        // (3) the 8 waiting threads release the other 504
}
  1. Arrive. After the local __syncthreads, thread p of block b writes flag 1 into GPU p's mailbox at [b][me]. The write is a compare-and-swap 0→1 that spins while the slot is still 1 (putFlag, ipc_gpu_barrier.h:37-41). That spin is back-pressure: if GPU p has not yet consumed my flag from the previous barrier, I cannot post the next one, so two consecutive barriers can never be confused. This is why no epoch counter is needed.
  2. Wait. The same thread then spins on its own mailbox slot [b][p] until GPU p has written 1 there, and consumes it with a CAS 1→0 (waitFlag, lines 43-47). Consuming resets the slot for the next barrier. All spinning is on local memory (my mailbox lives in my HBM); only the arrive-write crosses XGMI. Eight threads spin in parallel, one per peer.
  3. Same block index only. Block b on GPU 0 synchronises with block b on GPUs 1..7, never with block b+1. That is enough because the index range a thread processes depends only on its global thread id (idxStart = gtIdx·countPerThread, stride gridDim·blockDim·countPerThread, all_reduce_dda.h:29-34), so block b reads exactly the elements that block b on the peers wrote. 24 small barriers instead of one grid-wide barrier: no block ever waits for a slower block it does not depend on.
  4. Memory ordering is chosen per barrier by the two template flags (ipc_gpu_barrier.h:114-126):
callfence typearrive writewait readwhy
flat after copy-in; tree after reduce-scatterRELEASE_ACQUIRErelease CASacquire CASmy stores to scratch must be visible to the peer before it sees my flag; the peer's stores must be visible to me after I see its flag
tree, first barrierACQUIRE_ONLY (prev=false)relaxed CASacquire CASthe kernel has written nothing yet (the staging memcpy completed under stream order), so nothing to release; still need to see the peers' staged data
last barrier of both kernelsRELEASE_ONLY (next=false)release CASrelaxed CASpublish "I finished reading your scratch"; I read nothing after, so no acquire

The CAS is __atomic_compare_exchange_n with the chosen order on a uint32_t in uncached memory (ipc_gpu_barrier.h:30-33). On MI300-class GPUs a release/acquire atomic on fine-grained memory is what orders the preceding 16-byte stores (which went to HBM uncached) against the peer's subsequent XGMI loads.

What the last barrier buys, and what the kernel does not do. The trailing RELEASE_ONLY barrier exists because the scratch is reused by the very next all-reduce on the same stream. Without it GPU 0 could start the next call's copy-in while GPU 5 is still reading GPU 0's scratch from the previous call. There is no double buffering and no epoch: one scratch, serialised by barriers. Consequently a DDA all-reduce cannot overlap with the next DDA all-reduce of the same communicator, and two communicators each get their own scratch and mailbox (per-ncclComm state, comm.h:621-626).

6. Launch geometry: how many CUs it takes

getGridAndBlockDims (CollCommon.h:195-221): 512 threads per block (8 wavefronts of 64), each thread handles 16 bytes per loop step (uint4 = 8 bf16 or 4 fp32), grid capped at DDA_IPC_MAXBLOCKS = 24 (ipc_init_detail.h:18, the value in our log). Small messages get one partially filled block; large ones 24 blocks and a grid-stride loop.

Grid is computed from the full count (dda_all_reduce_ipc.cu:70) even for the tree kernel, which only loops to count/8; so in two-shot up to 7/8 of the launched threads exit their loop immediately. Harmless but worth knowing when reading profiles.

So DDA occupies at most 24 of the MI355X's 256 CUs and never more than 24 × 512 threads, for any size. The classic ring kernel at the same sizes runs on up to 112 channels (one block each). In a model server this matters twice: the all-reduce kernel leaves the rest of the GPU free for the compute kernels queued behind it, and its single launch has no proxy-thread or channel setup. Bandwidth is not the constraint here: at 64 MiB two-shot the 1.75 × 64 MiB = 112 MiB of XGMI reads per GPU are spread over seven links.

7. What DDA does not do, and what that means for a tuner

  • No algorithm/protocol/channel choice. The kernel is fixed; the only knobs are the two env vars (RCCL_DDA_ENABLE, RCCL_DDA_THRESHOLD) and the compiled constants (256 KB split, 24 blocks, 64 MiB scratch). NCCL_ALGO, NCCL_PROTO, NCCL_MIN/MAX_NCHANNELS, the built-in CSV tuner and any tuner plugin act on ncclEnqueueCheck, which a DDA call never reaches (Fig. 1).
  • No pipelining. Copy in, barrier, reduce, barrier. Latency is the sum of the phases; there is no overlap of the reduction with the transfer as in ring/LL. It wins because the phases are short and the fabric is fully connected.
  • No support for other ops (min/max/prod/avg), integer types, fp8, non-8-rank communicators, multi-node, grouped calls, or sizes above the scratch. Those fall back to the classic path and are tuner-visible.
  • Measured on our cluster: RCCL as shipped (DDA) beats the best classic-path configuration by 8-29% tok/s at every decode size we ran (campaign C, results-tuning/2026-09-14-2-sc2plusamd/SUMMARY.md), and stock SGLang's own AITER custom all-reduce beats DDA in turn (2026-09-10-2). Above 64 MiB, where DDA stops, the classic default is already the optimum (campaigns A and B', night_2026-09-14.html).

8. Same idea, one layer up: AITER's custom all-reduce

SGLang's AITER custom all-reduce is also a one-shot / two-shot direct algorithm over IPC-mapped peer buffers with a flag barrier. The difference is ownership of the buffers: AITER registers the model's tensors (or its own graph-captured buffers) with the peers once, so there is no per-call copy into a staging scratch and no host memcpy; DDA lives inside a generic library that receives arbitrary user pointers per call and must stage them. That staging copy (phase A / phase 0 above) plus the extra barrier it implies is the cost DDA pays for being generic, and it is the gap stock SGLang showed over the "none" arm (+2..+13% depending on size, 2026-09-10-2). Above 64 MiB AITER declines (_DEFAULT_CAR_MAX_SIZE = 8192·8192) and DDA is out of range, so those sizes are the only ones a TP-8 server ever hands to RCCL's classic path.
