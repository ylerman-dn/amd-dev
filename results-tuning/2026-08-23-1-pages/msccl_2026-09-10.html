1What MSCCL isread

MSCCL is Microsoft's runtime for custom, pre-synthesized collective algorithms. Its README: "an inter-accelerator communication framework that is built on top of NCCL and uses its building blocks to execute custom-written collective communication algorithms" and "MSCCL will always automatically fall back to a NCCL's generic algorithm in case there is no custom algorithm" (github.com/microsoft/msccl). AMD forked that into RCCL in 2.15.5 (ROCm 5.5, "Experimental support for MSCCL", CHANGELOG.md:244).

  • SCCL (PPoPP 2021): "synthesizes algorithms along the Pareto-frontier spanning from latency-optimal to bandwidth-optimal implementations of a collective", encoded as an SMT problem for Z3, for a given topology. Its cost model is the one that explains everything here: a message of size L on a link costs α + L·β, α the link latency, β the inverse bandwidth. Ring all-gather on 8 GPUs pays 7α; a latency-optimal algorithm pays diameter·α.
  • TACCL (NSDI 2023): same goal at cluster scale, using human "communication sketches" plus a mixed-integer program, because SCCL "did not finish synthesis for any combination" in 24 hours at modern sizes. Quote: "the commonly used Ring algorithm for Allreduce is not efficient for small input sizes as it has a high latency".
  • MSCCLang / msccl-tools: a Python DSL where you write the algorithm chunk by chunk; ncclize.py lowers it to the XML that RCCL ships ("Sends are split into send/recv operations and grouped by rank executing them. Within each rank operations are grouped under threadblock tags").
  • MSCCL runtime: a fork of NCCL whose kernel interprets that XML at run time using NCCL's own send/recv/reduce primitives. This is what sits inside RCCL as mscclRunInterpreter (section 6). Because it reuses the RCCL primitives, "MSCCL performs exactly the same as NCCL/RCCL if they use the same algorithm" (MSCCL++ paper, arXiv 2504.09014). Its whole gain is the algorithm, not the transport.

The algorithm RCCL ships for 8-GPU all_reduce is allpairs, written in allreduce_a100_allpairs.py. Its three comments are the whole algorithm: "Each rank sends the nth chunk to the nth rank into scratch space", "Each rank performs a local reduction on the nth chunk", "Each rank sends the fully reduced nth chunk to all other gpus". Two communication rounds on a fully connected topology.

Status in RCCL source: default-on for the MI300-class topology from 2.15.5 through 2.27.7 (our image); build-default off and "deprecated and will be removed" in 2.28.3 for ROCm 7.11 (CHANGELOG.md:14-15); removed entirely in the current develop docs ("MSCCL and MSCCL++ integration has been removed from RCCL", rccl-usage-tips, latest). AMD's own SGLang and vLLM tutorials launch servers with RCCL_MSCCL_ENABLE=0 without giving a reason, and the ROCm 7.1 system-validation page says to set it to 0 "to avoid data corruption/mismatch issue that existed in past releases". Whatever wins it brought are being handed to the frameworks' own kernels (section 4) and to MSCCL++ (section 7).

2When RCCL hands a call to MSCCLskim

Four gates, in order. All must pass or the call goes down the normal RCCL path (where the tuner lives).

Gate A: compiled in source

option(ENABLE_MSCCL_KERNEL ... OFF) at CMakeLists.txt:29 in the develop checkout; ON at tag rocm-7.2.0, which is what the container runs. Without it mscclEnabled() is hard-wired return false (msccl_lifecycle.cc:36-47) whatever the env says. Gate D: per-call filters source

  • All collectives enter via if (mscclAvailable(comm) && !mscclIsCaller()) return mscclEnqueueCheck(...) (collectives.cc:113, 165, 213, 261, 312, 341, 369, 394, 415).
  • AllReduce only: not FP8; bf16 only up to 8 MiB (collectives.cc:261-269).
  • No pre/post op: if (param->op >= ncclAvg) return (msccl_lifecycle.cc:355-357).
  • An algorithm file must match: same collective, nRanks, in-place vs out-of-place, minBytes <= nBytes <= maxBytes, and count % nchunksperloop == 0 (msccl_lifecycle.cc:373-393). First match in sorted filename order wins.
  • No match: mscclFallBackSavedParams re-calls the public ncclAllReduce with a caller flag set, so the second entry skips MSCCL and goes to ncclEnqueueCheck (msccl_lifecycle.cc:509-556).

For 8-GPU AllReduce the shipped files cover 0 to 20 MiB (LL to 64 KiB, LL to 512 KiB, Simple to 20 MiB). Above 20971520 bytes MSCCL declines and RCCL's own algorithms run.

3Why allpairs beats ring at small sizesread

Ring all-reduce on 8 GPUs is a reduce-scatter followed by an all-gather, each 7 sequential steps: 14 link latencies in series per call. On MI355X every GPU has a direct XGMI link to all 7 peers, so nothing forces a chain. The MSCCL allreduce_pairs schedule uses that: the same two phases, but each phase talks to all 7 peers at once.

Step it yourself, 4 or 8 GPUsread

Press Next. Both sides run the same reduce-scatter then all-gather; the only difference is who can talk to whom in one step.

What the XML actually schedules per GPU source: 8 reducer thread blocks (one per channel) plus 56 send/recv thread blocks, one per (peer, channel) pair. Each send/recv block does: send my 8 chunks of the slice that peer owns; receive that peer's 8 chunks of my slice into scratch; 7 reduces of scratch into my slice; send my reduced slice; receive the peer's reduced slice. Two communication rounds, 7-way parallel. Counts on GPU 0: 112 sends, 112 receives, 448 reduces.

Where this stops paying inferred: at large sizes the bottleneck is link bandwidth, not hops, and ring's steady streaming with many channels wins. That matches the shipped maxBytes of 20 MiB and the fallback above it.

4SGLang's custom all-reduceread

SGLang does not hand its tensor-parallel all_reduce to RCCL at all when it can avoid it. It carries its own all-reduce kernel, adapted from vLLM's custom_all_reduce (vLLM PR #2192, merged 2024-01-27). On ROCm the class that actually runs is AMD's copy in aiter, selected by default source: custom_all_reduce.py:392 if get_bool_env_var("SGLANG_USE_AITER_AR", default="true") imports aiter.dist.device_communicators.custom_all_reduce.CustomAllreduce and logs [AR] Using AiterCustomAllreduce (AMD default). All paths below are SGLang tag v0.5.17 and aiter commit d9e5ef7. Verified inside the actual container on amd-mi355x-5 (results-tuning/2026-09-10-2-aiterchk/): aiter at that commit, cap 64 MiB, and the stock servers logged [AR] Using AiterCustomAllreduce (AMD default) on all 8 ranks (at_stock_def/server.log on ses2-1) log.

Mechanism sourceread

  • Setup once. Each rank allocates an input staging buffer and a meta buffer (sync flags plus scratch) in uncached device memory, exports them with hipIpcGetMemHandle, exchanges handles over the torch TCP store, and maps every peer's buffers with hipIpcOpenMemHandle (aiter cuh 3410-3457; py 541-563, 929-931). After that every GPU can load from all 7 peers' memory with an ordinary pointer.
  • Barrier = one write. start_sync has each of the first 8 threads store a flag directly into the corresponding slot on every peer, then spin on its own slots. Comment in code: "simultaneously write to the corresponding flag of all ranks. Latency = 1 p2p write" (cuh 161-200). No atomics on peers, no host proxy thread.
  • One-shot (TP-8, under 80 KiB): each block's threads are split into 8 groups; group g loads chunk idx straight from peer g's input buffer, group 0 sums the 8 values in fp32 in fixed rank order and writes the result locally. Every GPU reads the whole vector from everyone and reduces it itself. One communication round. Bitwise identical across ranks by construction (cuh 393-394).
  • Two-shot (TP-8, 80 KiB and up): rank owns slice [rank*size/8, ...). Stage 1 reads its slice from all 8 inputs, sums, writes into its own scratch. end_sync with release/acquire. Stage 2 reads each peer's reduced slice from that peer's scratch into the local result. Two rounds, 7/8 of the bytes in each direction, same as MSCCL allpairs, without any RCCL machinery around it.
  • Split point (aiter cuh 3767-3778, the use_new path SGLang calls): TP-2 always one-shot; otherwise one-shot when ws <= 4 && bytes < 160 KiB or ws <= 8 && bytes < 80 KiB, else two-shot. At most 80 blocks. A "write mode" two-shot exists for 8 ranks above 4 MiB but only on gfx942; not on our gfx950.
  • Launches per call: one kernel, plus one device-to-device copy into the registered staging buffer when the input tensor is not itself registered (csrc/kernels/custom_all_reduce.cu:434). Under graph capture, input pointers are recorded and registered after capture (get_buffer_RD, cuh 3521-3545; register_graph_buffers), so the replayed graph has no copy and no host work.

Why it is faster than any RCCL pathread

  • Single kernel with direct peer loads. No proxy thread, no channel FIFOs, no per-step handshakes; the barrier is one remote store per peer.
  • Same two-round shape as MSCCL allpairs, but MSCCL still runs inside RCCL's interpreter over RCCL channels and primitives, with a work FIFO and a launch per call through hipExtLaunchKernel (section 6).
  • Graph-native: pointers registered once, no host nodes in the graph. vLLM's PR text on why NCCL costs more under graphs: "NCCL requires inserting more nodes per invocation. For example, NCCL requires a few host nodes to ensure proper operations."
  • Published upstream numbers (vLLM PR #2192, A100): Llama-70B TP-4 latency 16.37 s to 14.57 s, throughput 1761 to 1853 tok/s; "Latency improvement is more significant at smaller batch sizes, when allreduce is more latency bound." No AMD-published number was found for aiter's kernel vs RCCL.
  • Our number log: gpt-oss d32 decode TPOT 4.14 ms with the kernel vs 4.90 ms with MSCCL vs 5.35 ms with the tuned conf, same node, same day (2026-09-09-7-gptoss-attr/SUMMARY.md).

6The algorithm XML filesskim

So on 8 GPUs MSCCL covers only AllReduce and AllToAll. ReduceScatter, Broadcast, Reduce and 8-rank AllGather always go to RCCL's own algorithms and therefore to the tuner.

How a file becomes a kernel source: one interpreter kernel per (op, dtype, protocol), mscclRunInterpreter in src/device/msccl_kernel_impl.h:94-353. Each thread block copies its schedule to shared memory, sets up one send peer and one receive peer, then walks its steps, waiting on cross-block flags for dependencies. Launched once per collective call with grid = nBlocks, 256 threads (msccl_setup.cc:419-523). Not persistent. Protocols LL, LL128, Simple are the same RCCL primitives; the XML proto picks the entry.

Writing your own: the files are generated with Microsoft's msccl-tools (MSCCLang Python DSL) and dropped into MSCCL_ALGO_DIR. RCCL rejects files that use fused ops (RECV_REDUCE_SEND etc.) because all its kernels are built with fullOps=false (msccl_setup.cc:425-435, generate.py:605), and files needing more channels than NCCL_MAX_NCHANNELS are dropped with a WARN (msccl_lifecycle.cc:204-209).

7MSCCL vs MSCCL++skim

Same authors, different layer. MSCCL executes an algorithm inside NCCL/RCCL, with NCCL's blocking send/recv primitives. MSCCL++ throws those primitives away.

Inside RCCL source

  • MSCCL: RCCL's own interpreter kernel running XML schedules over RCCL's channels and transports. Compile option ENABLE_MSCCL_KERNEL, runtime RCCL_MSCCL_ENABLE, all collectives with a matching XML.
  • MSCCL++: Microsoft's separate library built as an external project (ext-src/mscclpp, 12 local patches, cmake/MSCCLPP.cmake), its nccl* symbols renamed to mscclpp_nccl*. Compile option ENABLE_MSCCLPP (OFF, only gfx942/gfx950, ROCm 6.2+), runtime RCCL_MSCCLPP_ENABLE default 0 since 2.27.7 (CHANGELOG.md:50). AllReduce and AllGather only, up to RCCL_MSCCLPP_THRESHOLD (16 MiB in code, init.cc:133; the docs say 1 MB), only under graph capture or with registered buffers unless forced (msccl_lifecycle.cc:607-641). It needs MSCCL's own gate to pass first (init.cc:2299-2301).
  • Order inside mscclEnqueueCheck: MSCCL++ is tried before MSCCL.

In our container nothing indicates MSCCL++ was active: the env receipts carry only RCCL_MSCCL_ENABLE, and an active MSCCL++ prints MSCCL++: Enabled! Msg size threshold=... at init (init.cc:2316). We did not grep for that line; the default-off plus no env var makes it very likely off inferred.

8Multi-nodeskim

No line in the MSCCL code says "single node only". The restriction falls out of gate C source:

  • rome_model_79 requires nNics = 0. NET nodes are removed from the topology only when system->nodes[GPU].count == comm->nRanks (src/graph/paths.cc:926-929), i.e. when the communicator is exactly this node's GPUs. A 16- or 40-rank communicator keeps its NICs, the model does not match, topo->mscclEnabled stays false inferred from that chain.
  • Escape hatch: RCCL_MSCCL_FORCE_ENABLE=1 bypasses gate C. Then an XML with the right ngpus must exist; shipped ones are 8, 16 and 32, and only AllGather for 16/32. CHANGELOG 2.26.6: "Added MSCCL support for AllGather multinode gfx942/gfx950 (i.e., 16 and 32 GPUs). To enable, set RCCL_MSCCL_FORCE_ENABLE=1" (CHANGELOG.md:78).

Consequence for our 2n to 5n sweeps: MSCCL was off there by construction (topology gate, and we also exported RCCL_MSCCL_ENABLE=0). The custom all-reduce is likewise intra-node only (section 4). Multi-node TP serving is the one deployment shape where every model all_reduce reaches RCCL and the tuner has a lever. Not measured.

10What the tuner can still touchread

The plugin is consulted in getAlgoInfo (src/enqueue.cc:2295-2305), reached only through ncclEnqueueCheck. Anything that leaves earlier never asks it. On one MI355X node running stock SGLang TP-8:

  • Custom all-reduce on: every model all_reduce up to 64 MiB is taken by SGLang's kernel, and the 91 to 94 MB prefill chunks by INT8 quick reduce (image env). RCCL sees one 4-byte call. Tuner lever: none. log
  • Custom all-reduce off, MSCCL on: all_reduce up to 20 MiB, alltoall up to 43 MiB go to MSCCL. Tuner lever: all_reduce above 20 MiB, FP8 all_reduce, bf16 above 8 MiB, and every other collective (reduce_scatter, broadcast, reduce, all_gather). source
  • Both off: the tuner sees everything. This is the only configuration our confs were ever measured in, and it is 34% below stock. log

Other collectives barely exist in these models. One rank's RCCL log per detect run (custom AR off, so RCCL saw everything; /data/ylerman/inmodel-2026-09-10/<model>/<mode>/detect/sc2_tun/logs/rccl.*.248.log on the nodes that ran them) log:

About 99% of calls are all_reduce. The fast paths cover other collectives unevenly: aiter ships custom all-gather and reduce-scatter kernels (all_gather_reg, custom_reduce_scatter, aiter py l.1202-1333) but SGLang uses them only on the data-parallel attention path behind SGLANG_DP_USE_REDUCE_SCATTER, not in plain TP serving (parallel_state.py:1036-1080, 2026-09-10-2-aiterchk/agchk.log); quick reduce is all_reduce only; MSCCL on 8 GPUs is all_reduce and alltoall only. So every non-all_reduce collective reaches RCCL and the tuner, and there is almost nothing there to tune.

MSCCL itself has no tuning surface from the plugin: no channel count, protocol or algorithm knob passes through getCollInfo to it. Its only knobs are the XML files (section 6) and NCCL_MAX_NCHANNELS, which can only drop files. Tuning MSCCL means writing a different XML.

Where a conf could still matter, all unmeasured: multi-node TP or PP serving (both fast paths are intra-node); models or sizes where SGLang falls back to RCCL for large all_reduce; collectives other than all_reduce; training.

11Trade-offsread

Both fast paths buy decode latency with generality. What they give up, from the same sources as above.

Custom all-reduce (aiter)

  • Memory. About 3 GB per rank per group reserved up front: 1 GiB staging plus 2 GiB flags and scratch (aiter py l.702, 958-969). That is KV-cache capacity gone. source
  • Bandwidth-wasteful by design. One-shot moves 7×L into every GPU and reduces the same data 8 times; two-shot runs on at most 80 blocks. Built for latency, weak at bandwidth, yet it takes every call up to 64 MiB with no size-adaptive switch to a streaming algorithm. Our prefill numbers agree: stock ahead of plain RCCL by 1 to 3% on TTFT against 19 to 28% on decode (2026-09-10-1-inmodel/REVIEW.md item 4). log
  • Narrow scope. all_reduce only; TP 2, 4, 6, 8; one node; full XGMI mesh assumed without probing; 16-byte aligned, contiguous tensors. Multi-node, other collectives, other shapes all fall to RCCL (aiter py l.646, 733-806, 1033-1060). source
  • Extra copy in eager mode. Unregistered inputs cost a device-to-device copy into the staging buffer per call (custom_all_reduce.cu:434). CUDA graphs avoid it, which is one reason graphs-off runs hid everything. source
  • Fragile primitives. Cross-GPU spin-waits on flags in uncached memory, relaxed/acquire/release ordering by hand, three diverging forks (vLLM, SGLang, aiter) with different thresholds and caps. A separate deterministic kernel had to be added for bitwise-stable serving. source
  • Above the cap, precision. In this image everything the custom kernel declines (over 64 MiB, in practice the 91 to 94 MB gpt-oss prefill chunks) goes to quick reduce with INT8 quantisation, because the image ships ROCM_QUICK_REDUCE_QUANTIZATION=INT8. Exact bf16 all_reduce for those chunks exists only on the RCCL path. Effect on output quality not measured. inferred
  • Opaque. Invisible to NCCL_DEBUG, -A 1, the tuner and rccl-tests. Every verification method this project built sees nothing. Only signal is RCCL's silence (one 4-byte call per run). log

MSCCL

  • Algorithm only. Transport is RCCL's: proxy, channels, FIFO, launch per call. "MSCCL performs exactly the same as NCCL/RCCL if they use the same algorithm" (MSCCL++ paper). Hence half the custom kernel's gain: 6226 vs 7316 tok/s. log
  • Static windows. 8-GPU allreduce up to 20 MiB, alltoall up to 43 MiB, nothing else; no FP8; bf16 only to 8 MiB; count % nchunksperloop == 0 or silent fallback. Adapting means writing a new XML with msccl-tools. source
  • Side effect on the whole communicator. The channel floor is raised to what the XMLs need (connect.cc:895-901), so other collectives run with more channels than RCCL would choose. source
  • Bypasses the tuner. The plugin is never asked for a call MSCCL takes. Anything you tune for those sizes is dead code while MSCCL is on. log
  • Being retired. Deprecated and build-default off in RCCL 2.28.3 for ROCm 7.11, removed in the develop docs. Known bugs: ncclCommSplit segfault (ROCm 6.4.1 notes), "data corruption/mismatch issue that existed in past releases" (ROCm 7.1 validation page). AMD's own SGLang and vLLM tutorials launch with RCCL_MSCCL_ENABLE=0. source
  • Single node. Topology gate needs 0 NICs in the communicator; multi-node only by force-enable, and only 16/32-rank allgather is shipped. source

Shared

  • Both depend on one node with a full XGMI mesh. Both are latency-optimal, not bandwidth-optimal. Both help decode, barely touch prefill.
  • Neither exists multi-node. There RCCL runs every all_reduce and the tuner keeps its lever. Not measured.
  • The MSCCL+flag arm was not split: part of its +8.8% over sc2 could be NCCL_MIN_NCHANNELS=112 rather than MSCCL. Open.
