DDA — RCCL 2.30.4's "direct" all-reduce, and why it took the tuner's job

2. Origin: Meta's torchcomms, ctran, rcclx — and what RCCL took

torchcomms

github.com/meta-pytorch/torchcomms: "a new experimental communications API for PyTorch" with "both the high level collectives API as well as several out of the box backends" (README). Backends: NCCL, NCCLX, RCCL, RCCLX, XCCL, Gloo. BSD-3. Meta-maintained.

Directory comms/common/algorithms/ holds Meta's own collective kernels: all_reduce/, all_gather/, all_to_all/, reduce_scatter/, plus CollCommon.cuh. The file all_reduce/all_reduce_dda.cuh exists there with the kernels ddaAllReduceFlatIpc and ddaAllReduceTreeIpc under "Copyright (c) Meta Platforms, Inc."

ctran

comms/ctran/README.md: "a solution to challenges in NCCL, providing a modular, self-contained architecture for collective communications across different GPU types (NVIDIA, AMD) and network topologies". It "explicitly prohibits dependencies on NCCL, NCCLX, RCCLX, or MCCL". In short: Meta's own transport/collective layer that can run beside or instead of NCCL's internals.

rcclx / ncclx

comms/rcclx/develop/ is a copy of the ROCm rocm-systems tree (dirs projects/, meta/, shared/) plus Meta scripts (rcclx_remerge.sh, apply_smart_patch.py, fb_upgrade_apply_internal_patches.sh): Meta's fork of RCCL with internal patches, periodically re-merged with upstream. ncclx is the same for NCCL. Meta also keeps MSCCL_STUB_APPROACH.md there: "Minimize changes to existing RCCL code by providing stub implementations for all MSCCL functions ... All MSCCL checks return false immediately" — Meta had switched MSCCL off in its fork before AMD deleted it upstream (PR #4340, 2026-04-13).

What AMD took, and whether RCCL now depends on Meta

PR #4958 "Direct Allreduce for scaleup" (Nusrat Islam, submitted 2026-04-13, merged 2026-05-17, commit c2c4b25f6d): "The work is inspired by the DDA allreduce algorithms in ctran/rcclx. The PR adds both one-shot and two-shot direct allreduce algorithms". The RCCL header src/include/algorithms/all_reduce/all_reduce_dda.h carries both copyrights and the line "Derived from Meta torchcomms comms/common/algorithms/all_reduce/all_reduce_dda.cuh". The kernel code is the same file, hipified.

Dependency: none at build or run time. The code is vendored (copied) into librccl.so. On the PR page a reviewer "questioned the maintenance strategy for code based on the rcclx fork. The author clarified they plan to maintain the code independently with planned optimizations rather than sync with rcclx." Since then AMD has indeed diverged: fabric/VMM variant for MI450 (#8155, 2026-07-14), LL and LL128 fast lanes, LL two-shot (#9748, 2026-08-21), GIN/LSA all-reduce (#10783, 2026-09-06), and a move to src/algorithms/dda/ (#10072, 2026-08-25). Why take Meta's kernels at all: they were measured (by Meta, then by AMD on MI350) to be 2-3x faster than RCCL's generic ring/tree for small and mid sizes on a fully connected XGMI node, and they were already written and tested against ROCm inside rcclx.

3. How it works — interactive walk-through

Setup (once, at communicator init, src/ipc_init.cu): each GPU allocates a 64 MiB scratch buffer (hipExtMallocWithFlags(..., hipDeviceMallocUncached)), exports it with IPC (hipIpcGetMemHandle), all 8 handles are exchanged with a bootstrapAllGather, opened (hipIpcOpenMemHandle), and the 8 resulting device pointers are stored in a table on the GPU (ddaIpcPeerPtrsDev). A second small IPC region holds the barrier mailboxes (8 ranks x 24 blocks x 8 flags).

Per collective: one kernel launch with up to 24 blocks x 512 threads (DDA_IPC_MAXBLOCKS 24). Every block handles a strided slice of the elements; every thread moves 16-byte vectors (uint4 = 8 bf16 values). The steps below are the kernel bodies from all_reduce_dda.h.

  

own data in scratchreduced resultdirect read over XGMIbarrier flags

The three building blocks, one line each

  • XGMI: the physical all-to-all mesh between the 8 GPUs. DDA's "direct" means a plain load from a peer's address (ipcbuffs[peer][idx]) travels over XGMI; no DMA engine, no proxy thread, no network stack.
  • IPC: how process A's kernel gets a pointer into process B's HBM. Done once at init; per collective it is just pointer arithmetic.
  • GPU barrier (IpcGpuBarrier::syncOnSameBlockIdx): "everyone has written its part, now everyone may read" — done with atomics in IPC memory, block-to-block, no host round-trip.

6. "Not ring, not tree" — what exactly is different

RCCL classic ring (what the tuner steers)

Data is cut into chunks; each chunk travels around a logical ring of 8 GPUs, 7 hops for reduce-scatter + 7 hops for all-gather, pipelined over N channels (each channel = one ring, one block of threads, its own FIFO buffers). Protocol LL/LL128/Simple decides the flag/packet format. Latency ~ 14 hops; bandwidth ~ full link bandwidth on the ring edges. The tuner picks algo (ring/tree), protocol and channel count per size; the CSV table encodes AMD's picks.

DDA one-shot

Every GPU reads the whole buffer of all 7 peers directly (7 x N bytes in, over the mesh in parallel) and reduces locally. 1 data hop, 2 barriers. Traffic per GPU = 7N read; wins while N is small (latency-bound). Threshold 256 KB.

DDA two-shot ("Tree" in the code)

Step 1: GPU r reads slice r (N/8) from all 7 peers and reduces it (reduce-scatter). Step 2: GPU r reads the reduced slice k from GPU k for all k (all-gather). 2 data hops, 3 barriers. Traffic per GPU = 2 x 7N/8 = 1.75N, the bandwidth-optimal minimum for all-reduce, without a pipeline. This is the "mesh in 2 jumps" pattern.

So: DDA is a different family of algorithm (direct / "mesh", Meta calls it Direct Data Access), not a tuned ring. Nothing in it can be steered by a conf: no channels (grid is fixed at up to 24 blocks), no protocol (plain 16-byte loads and a flag barrier), no chunk pipeline. The word "Tree" in ddaAllReduceTreeIpc is Meta's name for the two-stage variant and has nothing to do with RCCL's NCCL_ALGO=Tree. Newer RCCL (after our image) adds LL / LL128 protocol-style variants of DDA (flag-in-data, no barrier) with their own thresholds (RCCL_DDA_LL_ONESHOT_THRESHOLD 1 MB, RCCL_DDA_LL_TWOSHOT_THRESHOLD 16 MB, #9748) — still not tuner-visible.
