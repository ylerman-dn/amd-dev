This is a prediction, not a measured result

Every number here comes from the sweep, where each point is 3 repeats under mpirun with channels forced by environment variable. A shipped config is instead 7 repeats under srun with channels set through the tuner plugin. Those two paths have disagreed before — by 65% at 1 node, when the plugin interpreted a channel count in different units. So treat the P(sup) column here as a ranking hint, not the 0.95 gate: over 3×3 = 9 pairs, "1.00" is far weaker evidence than 1.00 over 49. Nothing here is shippable until an A/B confirms it.

The point of the exercise: at 3 nodes the config we shipped on 2026-08-04 kept 2 rules. This says the 1%-tolerance config would land 6, including a +15.6% at 256M the old one never captured. That is the case for changing the selection tolerance — and it comes from data already on disk.

Where config and default agree, ignore the percentage. At several sizes the config selects exactly what RCCL already does — 2-node 32K is TREE/LL/16 on both sides, yet the numbers differ by 9.3%. That is not a regression: shipping such a rule changes nothing. The gap is between an unforced run and a run forced to the same values by environment variable (1.510/1.490/1.510 against 1.500/1.370/1.370), across only 3 repeats.

Whether forcing genuinely changes what executes cannot be settled from this data: -A 1 reports a planned channel ceiling rather than what ran, and the sweep did not keep its NCCL_DEBUG=INFO logs, so the real channel{Lo..Hi} spans are unrecoverable. Those rows are drawn grey and dashed out of the table for that reason.

How to read the two scales

3 nodes has real headroom; 2 nodes mostly does not. At 2 nodes RCCL's default already sits at the 48-channel cap for everything ≥128K and only two sizes look beatable. At 3 nodes six do — and two of them (128M, 256M) are cases where the default appears to make a specific bad choice rather than merely leaving a little on the table.

The recurring pattern in the wins is an algorithm or protocol switch, not a channel tweak: TREE→RING at 32M on both scales, LL→LL128 at 128K–256K at 3 nodes, LL128→SIMPLE at 256M. That matches the 1-node story in reverse — at 1 node the wins came from raising channel counts, because the default there is loose.

Why we could not just measure it

The A/B needs a quiet fabric. On 2026-08-16 a co-tenant job (hai_test2, 4 nodes) was saturating the shared spine, and repeats of a single unchanged configuration ranged 1.5–25 GB/s. A preflight probe measured 599% spread at 2M on 3 nodes — the machine could not have decided anything, so no A/B was run.

That probe is now built into the harness as validate_tuner_config.py --preflight, which aborts before spending A/B time. Evidence: results-tuning/2026-08-16-4-fabricprobe/.

What an A/B would have to confirm

  • 3 nodes: 64K +2.6%, 128K +5.1%, 256K +11.7%, 32M +9.4%, 128M +10.9%, 256M +15.6%
  • 2 nodes: 256K +7.9%, 32M +11.4%
  • Everything else is within ±1% and should come back as "default already wins".
  • Any size where the plugin and env-var paths diverge would show up as a large disagreement with this table — which is itself worth knowing.

Because the prediction is written down first, the eventual A/B is a test rather than a fishing trip.
