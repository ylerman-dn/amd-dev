RCCL default vs tuned config

A 13-rule tuner config measured against stock RCCL across 18 message sizes. 2 of 13 rules survive, and the more interesting of the two is not a tuning win at all — it is a bug fix. RCCL’s 3-node default has a hole at 128M: bandwidth falls 7.8% as the message doubles from 64M, in every one of 7 repeats. Asking for 40 channels instead of the default’s 48 removes the hole and returns +10.2%. The other survivor, +8.7% at 32M, is an algorithm switch.

The finding: RCCL’s 3-node default has a hole at 128M

the headline result of this run · visible in both placements, in all 7 repeats
▲ Non-monotonic default

Bandwidth falls 7.8% as the message doubles from 64M to 128M

Bus bandwidth is supposed to rise with message size — bigger payloads amortise more launch and sync cost. The 3-node default does not: it reaches 268.78 GB/s at 64M, drops to 247.70 at 128M, then recovers to 297.87 at 256M. This is not the config misbehaving; it is the default, with no tuner loaded at all.

RCCL default tuned config (dashed) min–max of 7 repeats

The same five sizes as the right-hand end of the chart above, on a linear bandwidth axis, and the only chart here on which the fall itself is visible: the log-log sweep compresses it to four pixels, and the delta chart shows the config’s advantage at 128M without showing that the default got slower to earn it. Bands are min–max over 7 repeats. Values are labelled only where they carry the argument; the full 18-size table is below.

It is not noise, and the test does not depend on the median. Across the 7 repeats the two sizes do not overlap at all: the best 128M repeat is slower than the worst 64M repeat.

The default is not switching algorithm, protocol or channel count at 128M. All three sizes run RING / LL128 / 48. Only the message size changes, so the 48-channel schedule itself is what goes wrong at 128M.

Scope, and what would falsify this. The effect is present in the out-of-place column too (268.48 → 247.48 GB/s median), so it is not an artefact of the in-place path. It is one node triple (amd-mi355x-5,6,7), one RCCL build and one message-size ladder in powers of two — a sweep at finer granularity between 64M and 256M would locate the edge and is the obvious next step. The claim that 40 channels is the right number is not made here: 40 is simply the value the sweep proposed, and it is better than 48 at this size. The config’s own rise across 64M→128M is separated in every in-place repeat, but one out-of-place config repeat dips, so the “no hole at all” statement is scoped to the in-place column that this A/B ranks on.

Two real wins were thrown away by the config generator, not by the hardware

candidate.conf rule ranges vs the per-size measurements behind them
Tool limitation, not a hardware result

A rule is kept or dropped whole, and two rules each bundle a win with a loss

The validator drops any rule whose range contains a size that regresses more than 2%. That is the right policy — a range you ship must not contain a landmine. But two of the dropped rules contain a large verified gain sitting next to the regression that killed them.

# candidate.conf, and what the 7 repeats measured inside each range: allreduce,262144,1048576,tree,ll128,16 256K +8.9% 512K -5.0% 1M -3.8% -> DROP allreduce,268435456,536870912,ring,simple,32 256M +12.1% 512M -2.5% -> DROP

Both P(sup) values on those winning sizes are 1.00 and 1.00 — the config beat the default in all 49 repeat pairings at both. They are not marginal. The ranges are only that wide because generate_tuner_config.py merges adjacent sizes that happen to share identical settings, to keep the emitted config compact. The merge is what buries a +12.1% win next to a -2.5% loss and forces the validator to discard both together.

Two ways to fix it, neither of which needs another allocation: emit one rule per size and let the validator prune, accepting a longer config file; or teach the validator to split a mixed range at the sign change rather than discard it. The measurement is already done — these four sizes are verified at P(sup) 1.00 and the data is in this run folder. No hardware conclusion changes either way, which is the point: this is a +12.1% and +8.9% that the tool declined to ship, not a bandwidth that does not exist.

1, 2 and 3 nodes — the same method, three different answers

The 3-node default picks the identical channel count to the 2-node default at all 18 sizes — 2, 4, 8, 16, 32 and then 48 flat — which is why it is not drawn as a third bar. RCCL’s single-node defaults are loose. Its multi-node defaults are tight. That one sentence accounts for 8/12 becoming 1/13 and then 2/13: at 1 node the default runs 4K–256K on 1 to 16 channels and almost any increase wins; from 2 nodes up it is already pinned at its own 48-channel cap, so a tuner rule can only ask for fewer channels, and at 3 nodes 7 sizes did exactly that. 5 of them lost 2.5% to 5.0% (512K, 1M, 2M, 4M, 512M), one was inside the resolution floor — and one gained +10.2%. That one is 128M, the size where the default is broken. So trimming the channel count is a downgrade by default, and a fix only where the default’s own choice is wrong. Together with the TREE→RING switch at 32M that gives the two shapes a multi-node win can take: change the algorithm, or correct a specific default misstep. The 3-node run is the first to show the second shape, and it is the better target — a default that is wrong in a locatable place is more tractable than a default that is merely conservative.

One claim in this run’s SUMMARY.md is not supported by its own logs. SUMMARY.md states “plugin firing verified in all 24 per-rank logs”. This folder contains 7 config-arm per-rank INFO logs, of which 6 are non-empty — all from repeat 1, all from ranks 8–13 on amd-mi355x-6 — against 168 expected (24 ranks × 7 repeats), and 168 present for the default arm. The 1- and 2-node runs each retain the full set (56 and 112 per arm), so the shortfall is specific to this run folder; the config files’ mtimes (15:20:34–15:20:46, after the last default file) point at a copy that stopped part-way, and /opt/shared is not mounted on this VM, so the originals cannot be checked from here. Separately, --plugin-must-fire stops at the first log containing Applied config, so it never asserted all-rank firing in the first place. What is actually established: those 6 logs each carry TUNER/Plugin: Using DN-TUNER (v4) and 900 Applied config lines covering all 18 sizes with exactly the requested algo/proto/channels; the config arm’s own selection columns match the requested rule at 18/18 sizes in all 7 repeats, which is independent evidence that the plugin drove every rank; and no default-arm log contains a DN-TUNER line. Firing is not in doubt — the coverage of the log evidence is narrower than SUMMARY.md claims.

Three things this page does not claim. First, these busbw numbers are not comparable to the sweep-measured ones: the sweep reaches the GPUs by mpirun and this A/B by srun, which shifts absolute bandwidth. Every comparison here is between the two arms of this A/B only, which were launched identically — the A/B is self-contained, and no figure on this page is taken from a sweep. Second, at the smallest sizes busbw is printed to two decimals, so one least-significant digit is worth 9.1% at 4K, 4.5% at 8K, 2.3% at 16K and 1.2% at 32K — no difference smaller than that is even representable there. Four of the five smallest sizes came back exactly equal, and the two small non-zero changes are each exactly one count in the last printed digit (32K -1.19%, 128K -0.36%). That is why the ±1.2% floor is drawn on the delta chart and those sizes are reported as unchanged. Third, a co-tenant shared the fabric leaves during these runs. That moves absolute bandwidth for both arms and is a reason not to compare these numbers against another session’s, but it cannot manufacture the A/B contrast, which is interleaved within the same 3-minute window.
