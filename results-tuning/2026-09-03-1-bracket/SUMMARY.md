# Bracket-the-default sweep — allreduce 1-node, container stock RCCL (2026-09-03, node 4)

## Design (user-specified)
11 arms x 5 interleaved reps, `all_reduce_perf -b 4K -e 512M -f 2 -g 8 -n 20 -w 5 -c 1 -A 1`
inside `lmsysorg/sglang:v0.5.17-rocm720-mi35x` (image bakes `NCCL_MIN_NCHANNELS=112`), frozen
`librccl-tunerv4-dn.so`, per-size exact-match rules (`sw_bk_*.conf`, copies in this dir).

- `default`: no plugin (image default = 112 channels at every size; TREE/LL <=256K, RING/SIMPLE >=512K).
- `arm1..arm5`: per-size channel ladder x{0.5,0.75,1,1.25,1.5} around each size's OLD BARE-METAL
  default from the site table (4K-16K center 1, 32K:2, 64K:4, 128K:8, 256K/512K:16, 1M:32,
  2M/4M:52, 8M:54, 16M/32M:56), keeping that size's default algo/proto; >=64M carries {56,84,112,140,168}.
- `big1..big5`: rules ONLY at 64M-512M, channels {192,208,224,240,252} (256 wraps the 8-bit
  field and SIGFPEs — wszone finding).

Stats per (size, arm): median of 5 reps vs default arm; P(sup) = pairwise-wins fraction
(gate >=0.95); two-sided Mann-Whitney p. Full table: `analysis.txt` (generated by `analyze.py`
from the 55 stdout logs).

## Results
1. **Default (112 everywhere) wins or ties at EVERY size. No arm beats it anywhere**
   (0 of 180 size-arm cells pass the P(sup)>=0.95 gate upward).
2. **The old bare-metal per-size defaults are far below container default**: at their own centers
   (arm3 = exact old value) the loss vs 112 is -9% (4K) to -31% (2M/4M), worst -33% (8M),
   -26% (16M/32M). The old table's channel column does not transfer to this stack.
3. **>=64M confirms wszone**: 112-rule ties default (-0.2..-1.2%); everything above the comm
   channel count loses — at 64M ch>=140 collapses to ~221 GB/s (-37%); at 128M -17%; at
   256M/512M near-tie (-0.3..-0.6%). The whole 224-ladder (192..252) is flat at the same
   clamped plateau per size — the requested value above 112 does not matter.
4. **NEW FINDING (needs its own validation): plugin fallthrough is not neutral.** big1..big5
   have no rules below 64M, yet those sizes selected RING/LL instead of the no-plugin default
   TREE/LL at 4K-256K (busbw -19..-27%), and lost -20..-24% at 512K-8M despite `-A` showing the
   same RING/SIMPLE combo; at 16M/32M the gap closes to -0.3..-1.4%. plugin.c behavior on
   no-match (`dn/dn-tuner/plugin.c:409` and the fallthrough at the end of `pluginGetCollInfo`):
   `*nChannels = 0`, cost table untouched, returns ncclSuccess. So merely loading the tuner
   changes RCCL's selection path at sizes no rule covers. Mechanism unconfirmed (RCCL-side
   tuner integration); consequence: a partial conf can regress every uncovered size in
   rccl-tests-style traffic. In-model A/Bs to date compared plugin-with-conf vs NO plugin, so
   tuned arms silently carried this at their uncovered sizes.

## Hypotheses (not findings)
- The 512K-8M big-arm loss with an apparently identical RING/SIMPLE combo suggests the
  tuner-path channel selection differs from the native path when the plugin returns
  nChannels=0 (`-A`'s channel column is a known-unreliable planned ceiling; INFO `nc:` lines
  print 112 for all arms and are not usage evidence — wszone).
