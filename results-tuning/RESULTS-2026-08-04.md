## The one-line explanation of the whole result

**RCCL's single-node defaults are loose; its multi-node defaults are tight.**

At 1 node the default uses 1,1,1,2,4,8,16 channels for 4K–256K. Pushing the channel count up is
worth 12–63%. Every earlier experiment in this project forced channels *down*, which always hurt —
up was the untested direction.

At 2 and 3 nodes the default already sits at 48 channels (the measured multi-node cap) for
everything ≥128K, so there is nothing to gain by retuning channels. The multi-node wins that do
exist come from **algorithm choice** (TREE→RING at 32M) or from **correcting a specific default
misstep** — RCCL's 3-node default has a real dip at 128M, where busbw *falls* to 247.70 from 268.78
at half the size; 40 channels instead of 48 recovers +10.2%.

## What made this trustworthy — and what nearly did not

The measurement chain had five defects, all found and fixed today. Any one of them would have
produced confident nonsense:

| defect | consequence if unfixed |
|---|---|
| `-M 1` instead of `-A 1` | the sweep never saw what actually ran |
| `-R 1` (= `--local_register`) | silently altered performance |
| requested values recorded as measured | the previous config was **37% unfireable rules** |
| **`-C 1` (= `--report_cputime`)** | ranking on ~constant CPU time selected 1-channel configs **99% slower than default** |
| `validate_tuner_config.py` used 1 rank × 8 GPUs | the A/B would have measured a different topology from the sweep |

Two of those I introduced myself while "fixing" the others. The `-C` one is the instructive case:
the original bug (`-R`) was *masking* it, so correcting `-R` to `-C` made things worse. It was only
caught because the resulting config was visibly absurd (1 channel at 16M–64M) and I checked instead
of shipping it.

Also fixed: `optimize_metrics.py` now ranks on `busbw_ip` and drops rows where RCCL substituted the
request; `unsupported_combos.yaml` carries the measured acceptance map; the DB and CSV carry a
requested-vs-measured audit trail.

## The trap that cost 65.7%, and why it matters beyond this config

Where WarpSpeed is active (≥64M, 1 node) the plugin's `channels` field is the **post-multiplier
total**; `NCCL_MIN/MAX_NCHANNELS` sets the **base**. Same integer, 4× different meaning.

Our sweep measured `48` via env var. The config deployed `48` via plugin. Result: 12 base / 48
actual against the default's 56 base / **224** actual — **−65.7%**. `validate_tuner_config.py`
caught it and dropped the rule.

This is the "measurement path ≠ deployment path" failure that tool's docstring warned about,
measured here for the first time. It is also why the shipped config has no 1-node rule above 1M.
Any future sweep-to-config pipeline must translate channel units wherever WarpSpeed applies.

## Known limits — read before extending this

- **all_reduce only.** No other collective was swept.
- **RCCL 2.28.3-develop:2e42aa8.** The entire acceptance map is version-specific; a different RCCL
  may select differently.
- **Two real 3-node wins were lost to rule granularity**, not measurement: +8.9% @256K and +12.1%
  @256M were rejected because `generate_tuner_config.py` merged them into ranges that also contained
  a regression. Per-size rules would have kept 4 rules instead of 2. Recoverable.
- **Sweep busbw and A/B busbw are not comparable** — sweep uses mpirun outside Slurm and reads
  1–10% lower. Each A/B is self-contained (both arms `srun`, interleaved).
- **Co-tenants shared the fabric leaf switches** during multi-node runs. Affects absolute busbw, not
  the A/B contrast.
- The median-aggregation step between merge and optimize is **inline python, not part of the tool**.
  Without it `optimize_metrics.py` picks the single luckiest run out of 90 rows per size.
